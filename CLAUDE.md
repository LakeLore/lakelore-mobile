## Architecture in 30 seconds

**Three screens** (`src/screens/`):
1. `StateSelectScreen` — pan/zoom SVG **map of the US + Canada** (2026-07-15 all-states launch; `src/components/StateMapPicker.tsx`, geometry generated by `scripts/generateStatePaths.mjs` into `src/data/statePaths.ts`), plus a grouped A-Z list below the map as the accessible path. 50 states/provinces are active (45 US + ON/BC/MB/SK/AB; SC AZ MA DE RI QC are registry `active:false`, drawn muted, not selectable — AZ/MA/RI are presence/rating-thin, while DE/SC/QC now carry measured CPUE (2026-07-22/23 hunt) and are activation-eligible pending an owner call; CA/GA/MO are kept despite thin metrics per owner call 2026-07-15) — `src/activeStates.ts` derives `ACTIVE_STATES` from the generated registry export (`src/generated/states.ts`, regenerate with `node ~/lakelore-data/bin/export-mobile-states.js`). MN is free; every other state opens in **preview mode** for non-subscribers (see paywall section). Picking a state ALWAYS opens the county selector next (SearchScreen auto-opens it on every state change — the old "first visit only" gating was removed).
2. `SearchScreen` — species + lake-name search, advanced filters, list or scatter view. Scope selectors (**State + County**) sit together in a row at the top (`scopeRow`, DATA_MODEL §4 — County was moved up out of the filter chips). The in-search state switcher (`StatePickerModal`) uses the same map picker. Filter ranges + the scatter toggle are gated per state by the generated capability flags (`hasCpue/hasLength/hasCatch/hasStocking` in `src/generated/states.ts`). **Metric selection (DATA_MODEL_PROPOSAL_2026-07-20):** the **Measure** picker (`src/screens/search/MeasurePickerModal.tsx`) is the primary control and "Sort by" label, built from the server's `/measures` manifest. A **Measure** is what's quantified (Abundance / Avg Size / Stocking Impact / Presence — a small, stable set). The **Gear Type / Source** is NOT a separate control: a **2026-07-21 owner decision folded it into the Advanced Filters modal's "Gear Type" chips** (the DEFAULT is always one gear — the most-prevalent source for the scope — but the user may manually select more than one; with >1 selected, `activeSourceId` clears so the toolbar/scatter don't claim a single source; there is no `SourcePickerModal.tsx`). Selecting a measure adopts its default source (most records) automatically and sets `sortBy`/`sortDir` + the scope fields (`gearTypes`/`cpueKind`/`stockingFirst`/`presenceUnion`) via `applyMeasureSource`; the cascade default (Abundance → Stocking → Size → Presence) is `pickMeasure`/`pickSource`; picking a gear in Filters re-syncs `activeSourceId`. Presence has no ranking, so an incompatible sort can never linger (structural fix for the MB "Presence Only still offered Catch Rate/Stocking" bug). When `/measures` is unavailable (older server) the toolbar falls back to the legacy `SortPickerModal` + `defaultGearFor`. Measures load on species/county change and persist in the per-state session cache. Sort options no longer include Lake Size or Total Catch (Total Catch shows in the row's detail); MN's "Standard vs Targeted" survey-type filter was removed. The Measure picker is available in both list and scatter views. **Originally shipped as an OTA on runtime 1.1.0; now baked into the 1.1.1 (build 24) binary — no native module added.**
3. `LakeDetailScreen` — three tabs when the lake has size data, two otherwise: CPUE-over-time chart, **Avg Size over time** (2026-07-16: average length in inches, or average weight in lbs for MN which reports weight; tab hidden when the lake has neither; 0-valued averages are placeholder rows and are dropped), and stocking history with adults/100ac overlay. Renders in preview mode too (blurred name, county/acres hidden, source links suppressed, unlock banner).

**Scatter (`src/components/ScatterPlot.tsx`)** has a fixed axis rule (DATA_MODEL §4): **Abundance → Y, Avg Size → X, always** — the one place all sources of abundance vs size are compared, so it never remaps by measure. It plots ONLY abundance-vs-size: X is average length, or average **weight** where the state reports weight instead (MN, and the creel-weight states TN/GA — the generic branch picks weight when the result set carries it, mirroring the Avg Size measure), never anything else — a row without a size metric is dropped, and there is **no survey-year fallback** (a state with CPUE but no size just shows no scatter). Accordingly the **Scatter toggle requires both an abundance signal (`hasCpue || hasRating`) AND a size metric (`hasLength || hasWeight`)** — so pure-CPUE-no-size states like OK don't offer it at all (was silently plotting catch-rate-vs-survey-year, 2026-07-25). Because the result set is scoped to the selected Gear/Source, the Y (abundance) axis carries a single unit instead of stacking fish/net-night against fish/min-EF; the Y label prefers the active source's unit (`activeSourceId`). Colour = stocking density.

**County picker** (`src/components/CountyMapPicker.tsx`): geometry for 49 states/provinces (48 US states + Ontario) generated by `scripts/generateCountyPaths.mjs` into `src/data/countyPaths/` (keys match each state's canonical `lakes.county` values). States without matching geometry (RI towns, AK areas, and the other Canadian provinces' FMZs/regions — BC/MB/SK/AB) fall back to a list-only picker fed by the server's `/filters` counties.

**Forecast ratings (schema v4, 2026-07-15)**: ratings-tier states (GA/MO/IL/FL/KY/OK) carry the agency fishing-forecast `rating` (text) + `rating_ordinal` (state-local sortable scale) on the results wire — the "Forecast Rating" sort leads for those without CPUE. **Gear defaulting** (`defaultGearFor` in SearchScreen): picks the most common CPUE-BEARING gear for the current area+species (via `/filters` `gearCpueCounts`, so a synthetic presence bucket never hides real survey rows); when NO gear has CPUE (ratings/presence states) it falls back to the bucket with the most RECORDS (`gearTypeCounts`), preferring a primary signal over a fallback bucket (Presence Only / Trajectory / CPUE Normalized / Comprehensive / Mixed Gear) — e.g. IL defaults to 'Forecast Rating' over 'Trajectory', GA to 'Best Bet'.

**Species display names**: `src/generated/species.ts` (generated from the lakelore-data species registry) is the single lookup for all 56 states via `speciesDisplayName()` in `src/types.ts`; the legacy hand-maintained maps remain only as fallback for a few MN/ND/WI codes the registry doesn't alias.

Plus three modals: `PaywallScreen`, `AboutScreen` (sources + agency credits, accessible from State Select), and a Glossary inside SearchScreen.

**Navigation** (`App.tsx`): single `StateProvider` + native stack navigator. State selection is gated *before* the navigator mounts.

**State management**: lightweight. `StateContext` (which state is selected, persisted in AsyncStorage). `useEntitlement()` hook tracks subscription status. Per-screen useState for everything else; session cache in `SearchScreen` retains scroll/results when switching states.

**Data flow**: every screen fetches over HTTP from `lake-fish-api.fly.dev`. No bundled database. The API client (`src/api.ts`) sends an anonymous user UUID (`src/userId.ts`) as `X-User-Id` on every request.

## Paywall plumbing (locked 2026-05-11; preview mode 2026-07-08, expanded 2026-07-15)

- **Free**: MN. **Paid**: every other active state/province (44 US + 5 CA) via `LakeLore All-States` subscription at **$5.99/yr** auto-renewing. Active states derive from `lakelore-data/registry/states.json` on both server and app.
- **Preview mode (2026-07-15 shape)**: non-subscribers can ENTER paid states and do everything — pick counties, filter species, search lakes, browse list + scatter, see every metric, AND open `LakeDetailScreen` (full CPUE history + stocking). What's withheld is lake IDENTITY: the server nulls `lake_name`, `county`, `area_acres`, coords, and report/PDF links from paid-state `/results` AND `/lake/:id`, and replaces lake/survey ids with deterministic hashes (several states' raw ids embed the lake name). Rows/dot-cards/detail header render neutral redaction bars — block glyphs whose length varies deterministically per lake, deliberately NOT a plausible fake name (`src/components/BlurredLakeName.tsx`; decoys swapped out 2026-07-16, see the comment at the top of that file); county/acres lines drop out (fields are null); source-link blocks are suppressed in detail. Unlock banners in SearchScreen and LakeDetailScreen open the paywall. `preview` flag client-side: `!entitlementLoading && !isFreeState(state) && !hasAllStates`; server payloads carry `preview: true` (authoritative for LakeDetail rendering).
- **Provider**: RevenueCat. SDK key wired in `src/iap.ts`. Configured 2026-05-12.
- **Server gate**: paid-state `/pdf` returns 402 without entitlement (the PDF itself names the lake). Paid-state `/results` and `/lake/:id` serve non-subscribers in preview with identity redacted server-side, so names never reach an unentitled device. `/status` and `/filters` stay public (for marketing site stats).
- **No accounts**: anonymous device UUID identity. Reinstall = new UUID; user taps "Restore Purchases" to reattach Apple/Google account-level receipt.

See `~/APP_OPS.md` for full identifier inventory, subscription IDs, RC project ID, and the RC "credentials need attention" false-positive note.

## Build and run

```bash
# Dev (must be a native build — Expo Go can't load RC's native module)
npm run build:dev:ios          # produces a simulator dev client (~15 min)
npm start                      # `expo start --dev-client`, connects Metro to the dev client

# Preview (internal distribution; APK on Android, signed .ipa on iOS)
npm run build:preview:android  # APK for sideloading
npm run build:preview:ios

# Production (Play Store AAB / App Store .ipa)
npm run build:prod:android     # AAB for Play Store upload
npm run build:prod:ios

# Submit to stores
npm run submit:ios             # uploads latest production build to TestFlight
npm run submit:android         # uploads latest production AAB to Play Internal Testing
```

EAS config: `eas.json`. Project ID + owner in `app.json` `extra.eas`. Owner `ndrwtp` (personal Expo account).

## TestFlight iteration loop (preferred dev/test path on iOS)

The owner does day-to-day app testing on a **physical iPhone via TestFlight**, not the iOS Simulator. Simulator workflow is reserved for one-off debugging. When iterating on the app:

```bash
cd ~/lake-fish-mobile
npm run build:prod:ios && npm run submit:ios
```

Then wait for Apple processing (5–30 min after EAS finishes). TestFlight on the iPhone auto-updates the build; just open the app to get the new version.

**Total iteration time:** ~25–40 min per cycle (EAS queue ~5 min + build ~10 min + ASC processing 5–25 min). Batch UI/feature changes; don't ship one-line fixes through this loop.

**One-time setup (already done):**
- App Store Connect → LakeLore → TestFlight → Internal Testing → group "Internal" with `ndrwtp@gmail.com` as tester. Build 1.0.0 (3) was the first attached.
- Internal testers do not require Beta App Review — new builds become installable immediately after ASC processing.
- "Build Distribution: Automatic for Xcode Builds" in the group settings is misleadingly named — it auto-distributes EAS-uploaded builds to internal testers too.

**When you DO need the simulator** (e.g., to inspect a render bug Xcode/Hermes only shows in sim): use the dev build flow above. Known gotcha: macOS Simulator window can drop its GPU surface and show black; `xcrun simctl io <udid> screenshot` reads the framebuffer directly and bypasses the bug — that's the source of truth, not what the window shows.

## OTA updates (expo-updates)

`expo-updates` is wired and live on the `production` channel. JS-only fixes (copy, paywall blurb, network handling, anything inside the JS bundle) ship in ~2 min without a native rebuild and without re-submitting to the store.

```bash
cd ~/lake-fish-mobile
npm run ota -- --message "fix paywall typo"   # tsc --noEmit + jest gate first (2026-07-17, B5)
# Raw escape hatch (skips the gates): eas update --branch production --message "..."
```

That bundles the current JS, uploads to EAS Updates, and the next time any installed build with matching `runtimeVersion` cold-launches it picks up the new bundle. First production OTA was published 2026-05-13 (update group `bfed3391`, runtime `1.0.0`).

**Configuration (already done):**
- `app.json` `updates.url`: `https://u.expo.dev/<projectId>`
- `app.json` `updates.checkAutomatically: ON_LOAD`, `fallbackToCacheTimeout: 0`
- `app.json` `runtimeVersion: { policy: "appVersion" }` — runtime tracks `version`, so every native rebuild starts a fresh OTA pipeline.
- `eas.json` profile `production.channel: "production"` — builds emit on the production channel, OTA pushes go to the same channel.

**When OTA is NOT enough — you need a fresh native build:**
- Anything that changes `app.json` `version` (bumps `runtimeVersion` and orphans existing installs from new OTAs until they rebuild)
- Adding/removing a native module (changes the binary)
- Touching `app.json` plugins, permissions, or `infoPlist`
- Bundle identifier, icon, splash, or Privacy Manifest changes

For those, run the full `npm run build:prod:ios && npm run submit:ios` cycle and let the new build absorb both the native delta and the JS delta.

**Channels and branches:** EAS Update separates *branches* (versioned bundles you publish) from *channels* (what installed apps subscribe to). The mapping is in `eas.json`. We use a single `production` branch → `production` channel pairing for now; if we ever want a staged rollout, we'd publish to a `next` branch and re-point the production channel via `eas channel:edit`.

**Rollback:** `eas update:rollback --branch production` reverts the latest update — the next cold launch on any install picks up the previous bundle.

## Native config: what EAS prebuild does vs. what's on disk

The `ios/` (and `android/`) folder is `.gitignore`d. On every EAS Build, `expo prebuild` regenerates the native projects from `app.json` + the installed config plugins. So the truth about the production binary lives in `app.json`, **not** in any local `ios/LakeLore/Info.plist` you might see.

Two consequences worth knowing for App Review:

- **App Transport Security**. `app.json` `ios.infoPlist.NSAppTransportSecurity` sets `NSAllowsArbitraryLoads: false` plus `NSAllowsLocalNetworking: true` — a hardened combo that lets the dev server use HTTP on the LAN without globally weakening ATS. Because it's in `app.json`, EAS-built binaries carry it (overriding expo's more permissive default of `NSAllowsArbitraryLoads: true` with a localhost exception). If App Review asks, the rationale is: dev/preview builds reach a local Express API at `http://<lan-ip>:3100` via the local-networking exception — production builds only ever talk to `https://lake-fish-api.fly.dev` over HTTPS, so arbitrary loads stay off.

- **`exp+lakelore` URL scheme**. `expo-dev-client`'s config plugin (`node_modules/expo-dev-client/plugin/build/withDevClient.js`) calls `withGeneratedIosScheme`/`withGeneratedAndroidScheme` unconditionally — there is no dev/prod gate. So the production binary registers `exp+lakelore` alongside the real `lakelore` scheme. Apple has not been reported to flag this in practice, but if it ever does, the fix is to add expo-dev-client to `app.json` `plugins` with `{ "addGeneratedScheme": false }`. Leaving it as-is for now.

## Species code maps (src/types.ts)

Species display names come from the generated registry lookup (`src/generated/species.ts` via `speciesDisplayName()` in `src/types.ts`) for all 56 states — see the "Species display names" note in the architecture section. Only four legacy hand-maintained maps remain in `src/types.ts` (SD/MN/WI/ND), kept as fallback for codes the registry doesn't alias. **Codes are NOT interchangeable across states** — Common Carp is `CAR` in ND but `CAP` in MN/SD; same for several other species. See `~/DATA_PIPELINES.md` ND "Key Differences" for the full list of mismatches. Always verify a new code against `fish_catch.species` in that state's DB before adding it. For ND specifically, `fish_catch.species_name` carries the full name from ArcGIS, so the ND map can (and should) be regenerated from data after a re-scrape, not hand-edited.

## Important constraints

- **`@pagopa/io-react-native-integrity` is a native module (added 2026-07-16, ships with build 21+).** Powers App Attest / Play Integrity at session issuance (`src/attest.ts`, wired into `src/session.ts`; server side in lake-fish-mobile-server `server/attest.js`). It is LAZY-required and failure-soft, so OTA updates to pre-21 builds degrade to unattested sessions instead of crashing. It's an old-arch bridge module running through RN's new-arch interop — verify attestation works on the first build-21 TestFlight install (check `attested: true` lands in the `[attest]` server telemetry). `app.json` carries the App Attest entitlement + `extra.playCloudProjectNumber`; Android verification additionally needs owner console steps (~/APP_OPS.md "App Attest / Play Integrity").
- **Lazy-require is NOT enough for codegen-style native modules on older binaries.** `react-native-view-shot` 4.x calls `TurboModuleRegistry.getEnforcing` at MODULE SCOPE — on a binary without its native side (build ≤ 20), the `require()` itself crashed the app under the bridgeless runtime, below the reach of a surrounding try/catch (2026-07-17, share-card crash). The pattern that works: a pure-JS availability probe BEFORE any require — e.g. `globalThis.expo?.modules?.ExpoSharing` (a plain property read) — and only require the package when the probe passes (see `shareLakeCard` in LakeDetailScreen). Old-style bridge modules (`NativeModules.X ?? Proxy`, e.g. `@pagopa/io-react-native-integrity`) degrade safely without this; check which style a new dependency uses before trusting lazy-require on OTA-to-older-binary paths.
- **`react-native-purchases` is a native module.** Once it's in `package.json`, the legacy Expo Go QR-and-go dev flow doesn't work. Dev means a dev client; first dev build takes 10–15 min on EAS free-tier queue.
- **`@sentry/react-native` plugin requires `organization` and `project` in `app.json`** (set to `lakelore-app-llc` / `react-native`), OR `SENTRY_DISABLE_AUTO_UPLOAD=true` as a build env var. As of 2026-05-12 the Sentry source-map upload step fails with "Project not found" on every prod build (Sentry org/project/token config seems off — `SENTRY_AUTH_TOKEN` is set as an EAS project secret but apparently doesn't have access to the project), so the production profile in `eas.json` sets `SENTRY_ALLOW_FAILURE=true` — upload is attempted but a failure doesn't tank the build. The preview and preview-sim profiles skip the upload entirely with `SENTRY_DISABLE_AUTO_UPLOAD=true`. Runtime error reporting still works (DSN is set in `src/sentry.ts`); stack traces just aren't symbolicated via uploaded source maps. Revisit when launch dust settles.
- **iOS bundle ID and Android package name** (`com.lakeloreapp.lakelore`) are immutable post-publish — same for subscription product IDs. See `~/APP_OPS.md` for the full identifier table.
- **No `ios/` or `android/` folder** is committed — managed Expo workflow. Native code regenerates from `app.json` on every EAS build.
